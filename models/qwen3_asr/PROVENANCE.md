# Qwen3-ASR / Qwen3-TTS released-kernel provenance

Read-only investigation on host `70`. I did not rebuild any kernel. A row is marked
**md5 verified** only when an `.axmodel` left in a host build directory, or the copied
kernel in `lineC/k`, has the same full MD5 as the released file. The release MD5s are in
`work/Qwen3-*.md5`; the release-name lists are `prov/qwen3_*.files`.

## Scope and terminology

- After intersecting the release manifests with rows that are `-` in `/tmp/q_rel/*.tsv`,
  the unmatched scope is **20 ASR kernels per model** and **160 TTS kernels per model**.
  The TSVs also contain older unmatched names that are not in these release manifests;
  those are outside this report's scope.
- Surviving MD5-identical artifacts were found for **7/20 ASR kernels** per model and
  **6/160 TTS kernels** per model. The other files remain unverified; their family and
  generator are reported where evidence supports it, without claiming an exact build.
- **Recorded** means the command or job line survives verbatim. **Reconstructed** means
  the script and the name-forming parameters are established, but the literal invocation
  does not survive. Values shown as defaults are source defaults, not proof that the
  environment variable was unset.
- All surviving relevant `lineC` build contexts have `toolchain_version: "8.0"` and
  `toolchain_commit: "7913a059"` (`build_context.json:2-3`). The two surviving
  `dsl-gen/out_mm` contexts instead have `toolchain_version: "8.0"` and
  `toolchain_commit: "9108a9b4"`.
- The TTS 0.6B and 1.7B released files are byte-identical and were generated from the
  same shape lists. Their tables therefore describe the same artifacts twice.

## What could not be established

- **ASR `mm_bf16_*`:** none of the four kernels per model has a surviving artifact with a matching MD5. No shape list, job line, output directory, or source-tree binding was found. The identical name syntax makes `ggml/mm_kernels.py` a plausible generator, but I did not establish that it built these files.
- **ASR front-end coverage:** only 2 of the 8 `qwen3a_fe_*` outputs and 1 of the 4 `qwen3a_fe2_*` outputs per model survive. The other output MD5s could not be reproduced or found. The failing ones cannot have their `WB`, `XB`, or `TO` settings attributed beyond the source defaults.
- **ASR layer settings:** the two outputs per model are MD5-verified, but no literal `q3a_layer.py` command survives. `MODEL`, `N`, `CORES`, `DUMP`, and `NREAL` (116 for N=128, 52 for N=64) are fixed by paths/logs; explicit `KEEP_SHM` and `LAYER` values are not recorded.
- **TTS `mm_bf16_*`:** only 2 of 46 outputs survive. The exact 46-shape `SHAPES` value can be reconstructed from release names, but no log proves that they were built together, and the actual `XB`/`YB` values and invocation are missing. `dsl-gen` has no git history; only byte-equality of its script to commit `9695d3b` is provable.
- **TTS plain `conv1d_*`:** only 2 of 57 outputs survive. The source bytes are pinned to `64f9071` (also `b3c60fb`), but the exact worktree used at 00:55 is not recorded. Source mtime makes `dsl-qwen3` likely, not proven. Exact `WB`/`XB` and the literal batch command are missing. `dsl-gen/k` also has `conv1d_bf16_ic96_oc1_k7_d1_l138246_npu4`, but its MD5 is `2ee970a1e42740f772dd806b2a3a2a48`, not the released `d64d4a4deba21ee55627ffe06681c283`, so it is not counted.
- **TTS `_b` / `_br`:** 1 of 45 and 1 of 12 outputs survive. The worktree and dirty-tree state are pinned (`dsl-voc` HEAD `8dcd1bb`, later commit `0805ce0`), but the literal invocations and `WB`/`XB` values are missing, as are the outputs for the rest of each shape batch.
- No build was run to search for a different set of tiling parameters. Therefore “verified” here always means an existing artifact matched, not that a reconstruction was demonstrated to reproduce the MD5.
